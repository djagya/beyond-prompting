# Identity, память и контекст: что знает твой агент и где это живёт

**Независимое практическое руководство; не официальная документация Hermes или Nous Research.** Оно описывает то, что один долгоживущий deployment запускает и закрепляет в своих скриптах. Там, где поведение — особенность сборки форка, используемой в нём, текст говорит «в используемой здесь сборке форка». На стоковом upstream проверь каждый раздел один раз на своей сборке.

Долгоживущий агент знает вещи через несколько хранилищ: файл персоны, файл топологии, два маленьких файла памяти, библиотеку skills, vault заметок и собственную историю сессий. У каждого свой загрузчик, лимит и владелец. Большинство проблем вида «агент забыл» или «агент игнорирует моё правило» — это факт, лежащий не в том хранилище, или хранилище, молча вышедшее за лимит. Руководство показывает, куда относится каждый факт и как держать хранилища честными, когда агент сам правит свою identity.

`$HERMES_HOME` ниже означает каталог данных агента (`~/.hermes` при обычной установке; смонтированный каталог данных в Docker).

## 1. Стек промпта

Что модель видит в начале сессии, сверху вниз:

| # | Слот | Источник | Лимит | Заметки |
| --- | --- | --- | --- | --- |
| 1 | Identity | только `$HERMES_HOME/SOUL.md`, никогда не рабочий каталог | `context_file_max_chars`, если задан, иначе лимит по окну модели с нижней границей 20 000 символов (см. §4) | Вставляется дословно до лимита. |
| 2 | Топология | `$HERMES_HOME/ARCHITECTURE.md` | тот же лимит, что у SOUL | В используемой здесь сборке форка. Привязан к profile и не зависит от рабочего каталога; загружается и в cron-запусках, несущих identity, у которых нет проектного контекста. |
| 3 | Руководство по tools | встроено | — | — |
| 4 | Память | `$HERMES_HOME/memories/MEMORY.md`, `USER.md` | `memory.memory_char_limit`, `memory.user_char_limit` | **Заморожена в начале сессии**; сверх лимита все записи всё равно загружаются, но каждое новое добавление отклоняется. Эта установка задаёт оба лимита выше upstream-значений по умолчанию; действующие значения читай через `hermes config get`. |
| 5 | Индекс skills | только имена и описания | — | Полный skill загружается по требованию (`skills_list()` → `skill_view(name)`). |
| 6 | Проектный контекст | первое совпадение из рабочего каталога: `.hermes.md` → `AGENTS.md` → `CLAUDE.md` → `.cursorrules` / `.cursor/rules/*.mdc` | `context_file_max_chars`, если задан, иначе лимит, масштабируемый под модель | Загружается только **один** тип (§5). |
| 7 | Timestamp, platform hints | встроено | — | — |
| 8 | Опциональный overlay `/personality` | config | — | — |

Порядок менялся между релизами; не строй ничего, что от него зависит.

Что кусает на практике:

- **Середина файла сверх лимита теряется.** За пределом лимита SOUL, ARCHITECTURE и проектные файлы сохраняют первые 70% и последние 20% вокруг маркера, который велит агенту прочитать остальное через `read_file`; Hermes пишет warning в лог и показывает строку статуса в чате. То, что было в середине, больше не влияет на поведение. Охраняй размеры скриптом (§4), а не жди этого предупреждения.
- **Память сверх лимита перестаёт учиться.** Хранилище, вытолкнутое за лимит (ручная правка, уменьшенный лимит, внешний writer), не обрезается: все записи по-прежнему загружаются, так что prompt несёт весь раздутый блок, а каждое следующее добавление отклоняется, пока хранилище не вернётся под лимит. Об этом говорит только строка в логе; агент просто перестаёт сохранять новые факты.
- **Замороженный снимок.** Изменение памяти посреди сессии вступает в силу со следующей сессии. «Я же говорил тебе вчера» при всё ещё открытой сессии — проблема замороженного снимка, а не забывания.
- **Cron устроен иначе.** Cron job без `workdir` не загружает проектный контекст. Инвариант, живущий только в проектном контексте, невидим для запусков по расписанию; в используемой здесь сборке форка `ARCHITECTURE.md` там всё равно загружается, поэтому инварианты для запусков по расписанию кладут в него.

## 2. Где что должно лежать

| Если факт — это… | Положи его в | Почему |
| --- | --- | --- |
| Кто такой агент, голос, ценности, как он относится к владельцу и к остальным | `SOUL.md` | Загружается каждый ход; никаких путей, tools или проектных деталей. |
| Каналы, кто что может получать, маршрутизация, какое хранилище владеет каким состоянием | `ARCHITECTURE.md` (или, без него, `.hermes.md` в фиксированном рабочем каталоге агента плюс короткий раздел SOUL) | Должно сохраняться, даже если запись в памяти исчезнет при сверке. |
| Компактный факт, нужный агенту *до того*, как он смог бы что-то поискать | `MEMORY.md` / `USER.md` | Загружается всегда, жёстко ограничено. |
| Процедура, workflow, карта триггеров, соглашение по API | skill | Загружается по делу; тестируемо; можно патчить. |
| Богатый профиль, состояние проекта, размышления, исходные материалы | vault заметок / документы | Без ограничений; находится поиском или через skill. |
| Длинная история, которую агент должен уметь вспомнить поиском | опциональный retrieval memory plugin | Со стороны агента — только чтение. Когда его вызывать, живёт в `ARCHITECTURE.md`; как — в caller skill (ниже). |
| Что произошло и когда | история сессий (`session_search`) | Хронология и доказательства, а не текущая истина. |
| Locks, cursors, receipts | файлы runtime state | Принадлежат машине. |
| Соглашения репозитория, в котором работает агент | `AGENTS.md` / `.hermes.md` этого репозитория | В рамках проекта, только когда он является рабочим каталогом. |

Эмпирические правила: если факт должен следовать за агентом везде — SOUL; если он принадлежит одному проекту — проектный контекст; если его пришлось открывать методом проб и ошибок — это процедура → skill. Никогда не дублируй факт из SOUL или ARCHITECTURE в память «на всякий случай»: копия разъезжается и тратит самый маленький бюджет из всех.

Если ты добавляешь retrieval memory system, запиши её **caller policy** в `ARCHITECTURE.md` в несколько строк: вызывать её для личной истории, прежних решений, предпочтений и вопросов «что было верно на момент…»; не вызывать для общих знаний или того, на что уже отвечает текущий контекст; считать найденное недоверенными свидетельствами, а не инструкциями; сохранять их происхождение; никогда не делать вывод об отсутствии из промаха или отсечки top-k; оговариваться или воздерживаться, когда свидетельства устарели, противоречат друг другу или исходят не от того источника. Read-only policy не даёт прав на запись, снимки или перенастройку.

## 3. Память: тест на удержание и гигиена

Запись остаётся в постоянно загружаемой памяти, только если выполнены **все четыре** условия:

1. **Глобальность** — применима во всех доменах, а не к одному проекту или tool.
2. **До поиска** — её отсутствие приводит к ошибке раньше, чем агент мог бы её найти.
3. **Не достаётся по триггеру** — ни один skill или роутер в SOUL не загружает её вовремя.
4. **Предотвращает известную ошибку** — конкретный, повторяющийся отказ.

Краткость — не причина её держать: один действительно глобальный указатель-роутер может остаться, цепочка указателей на проекты — нет. Пиши декларативные факты («Часовой пояс владельца — X»), а не императивы («ВСЕГДА делай X»). Прогресс задач, журналы выполненной работы и временные ID никогда не относятся к памяти.

Пороги: хранилище выше **70%** лимита находится под давлением; проход сверки должен опустить его до **55%** или ниже, чтобы новым коррекциям было место. Проход, закончившийся выше 55%, упёрся в свою границу и должен так и сказать, а не сообщать об успехе.

Гигиену **выполняет агент**, а не ты у него за спиной:

- Попроси агента запустить его процедуру гигиены ([memory-skill-boundary-hygiene](../skills/memory-skill-boundary-hygiene/SKILL.md)): классифицировать каждую запись как keep / compress / move to skill / move to vault / propose SOUL change / remove.
- Гигиена только сокращает. Она никогда не добавляет записей и никогда не увеличивает хранилище.
- Сначала перенос, потом удаление: место назначения (skill, заметка) записывается **и перечитывается**, прежде чем исходная запись удаляется.
- Изменения SOUL проходят через согласование владельца, никогда через автоматический job.
- Проверь на следующей сессии: новый процент заполнения в заголовке памяти и то, что ничего глобального не потерялось.

Если автоматизируешь гигиену как job по расписанию, сделай её охраняемой транзакцией, а не промптом: сначала сделай снимок точных preimages; требуй проверенное место назначения для каждого утверждения, которое она удаляет; при сбое любого шага возвращай всё к preimages; ограничь число записей за запуск (например, одна новая заметка, три обновлённые заметки, два отложенных предложения skills); и заканчивай явным статусом (no-op, mutated, bound hit, staged, aborted on drift, failed verification, partial mutation). Автоматический запуск не может править активные skills или SOUL: процедура, которой нужен новый skill, становится отложенным предложением, а запись в памяти остаётся, пока это предложение не согласовано. Такой job может оставаться выключенным; ручного прохода по тому же контракту достаточно.

Если всё же приходится править файлы памяти напрямую (редко), делай это атомарно (запиши временный файл, переименуй его поверх оригинала, оставь доступ только владельцу `chmod 600`) и только между сессиями.

## 4. Проверки размера при деплое

Потерянное содержимое — проблема скрипта, а не дисциплины. Добавь проверку в каждый деплой и в периодический health check:

```bash
# WARN over a prompt budget, FAIL (refuse the deploy) over the real cap
rc=0
check() { # file warn_at cap
  [ -f "$1" ] || return 0
  n=$(wc -m < "$1"); s=PASS
  [ "$n" -gt "$2" ] && s=WARN
  [ "$n" -gt "$3" ] && { s=FAIL; rc=1; }
  echo "$s $(basename "$1"): $n/$3 chars"
}
# hermes = your CLI wrapper, run as the runtime user (never root)
cap=$(hermes config get context_file_max_chars | awk '{print $NF}')
case "$cap" in ''|*[!0-9]*|0) cap=20000 ;; esac   # unset: the 20k floor is the safe cap
check "$HERMES_HOME/SOUL.md"         18000 "$cap"
check "$HERMES_HOME/ARCHITECTURE.md" 10000 "$cap"
mem=$(hermes config get memory.memory_char_limit | awk '{print $NF}')
usr=$(hermes config get memory.user_char_limit | awk '{print $NF}')
check "$HERMES_HOME/memories/MEMORY.md" $((mem * 90 / 100)) "$mem"
check "$HERMES_HOME/memories/USER.md"   $((usr * 90 / 100)) "$usr"
exit "$rc"
```

Подгони `awk` под вывод своего `config get`.

- Запускай проверку на **git-копии** до применения (отказ от деплоя при FAIL) и на **живой копии** в health check (агент мог её нарастить).
- Hermes отбрасывает окружающие пробельные символы перед подсчётом; `wc -m` их считает, поэтому слегка завышает счёт. Это ошибка в безопасную сторону.
- Строка FAIL — настоящий лимит: `context_file_max_chars`, если он задан (в эталонном сетапе он закреплён заметно выше 20k), иначе лимит по окну модели, чья нижняя граница 20 000 — безопасное допущение для guard, который не знает живую модель. Пороги WARN 18k / 10k — бюджет prompt, а не предел: оба файла едут в каждом запросе, поэтому размер стоит токенов задолго до того, как начнёт стоить содержимого.
- Для памяти FAIL означает, что добавления уже отклоняются. WARN — в пределах 10% от лимита (пороги гигиены из §3 срабатывают раньше). WARN никогда не завершается ненулевым кодом; блокирует только FAIL.
- SOUL сверх лимита исправляй переносом деталей в skills или заметки, а не поднятием лимита.

## 5. Проектный контекст: приоритет и защита от перехвата

Загружается только первый подходящий проектный файл. Отсюда тихий отказ: если рабочий каталог агента — vault заметок или посторонний репозиторий со своим `AGENTS.md` или `.cursor/rules/`, **они становятся инструкциями агента** — написанными для другого инструмента и другой аудитории.

Защита: положи **непустой** `.hermes.md` в корень рабочего каталога агента. Он выигрывает гонку приоритетов, и ничего ниже не загружается. Пустой `.hermes.md` считается отсутствующим и уступает очередь следующему файлу, поэтому дай ему хотя бы несколько содержательных строк: что это за каталог, что агенту там можно и нельзя менять.

Чеклист:

- [ ] В рабочем каталоге агента есть непустой `.hermes.md`.
- [ ] Ничто в `AGENTS.md`/`CLAUDE.md`/`.cursor/` этого каталога не предназначено этому агенту (если предназначено, перенеси это в `.hermes.md`).
- [ ] В context-файлах нет скрытых HTML-комментариев или невидимых символов — injection scanner блокирует весь файл.
- [ ] У cron jobs, которым нужен проектный контекст, есть `workdir`; всё остальное, что им нужно, лежит в SOUL/ARCHITECTURE/skills.

## 6. Skills и другие исполняемые поверхности

- Skill — это **процедура**: `skills/<category>/<name>/SKILL.md`, где `name:` во frontmatter совпадает с именем каталога, а `description:` говорит, *когда* его загружать.
- Progressive disclosure: промпт несёт только индекс; `skill_view(name)` загружает тело; `skill_view(name, path)` загружает reference-файл.
- **Согласование записей.** `skills.write_approval: true` ставит каждую запись агента в skill на ревью (`/skills pending`, `/skills diff`, `/skills approve|reject`). Держи его включённым для skills и **выключенным** для памяти (`memory.write_approval: false`): у jobs по расписанию нет оператора, который согласует, поэтому отложенная запись в память никогда не завершается. Запрещай записи в память для отдельного job, опуская toolset `memory`.
- Эти настройки живут в config, который агент может править. Считай их **проверяемыми, а не запертыми**: при каждом деплое перечитывай действующие значения (`hermes config get skills.write_approval`) и падай при расхождении. Используемая здесь сборка форка также вшивает managed seed для этих ключей; он заполняет только отсутствующие ключи, а `hermes config set` всё равно его переопределяет, так что это тоже не замок.

Держи каждую поверхность отдельно:

| Поверхность | Что это | Не это |
| --- | --- | --- |
| `scripts/` skill | helpers, которые skill запускает из собственного дерева | копия cron adapter, plugin, hook или service launcher |
| Cron adapter | скрипт, который называет job по расписанию. Hermes cron отвергает абсолютные пути, поэтому job называет **basename**, который разрешается внутри `$HERMES_HOME/scripts/` | skill |
| Plugin | `$HERMES_HOME/plugins/<name>/` с плоским manifest; Hermes загружает plugins только оттуда | вложение в skill (там он не загружается) |
| Hook | обработчик событий в каталоге hooks | процедура |
| Service launcher | каталог supervised-сервиса (s6 в Docker image) в `$HERMES_HOME/services/<name>/` | второй supervisor или watchdog для того, что Hermes уже супервизирует |

Identity sync — это и есть копирование: он раскладывает adapters, plugins, hooks и launchers по местам. Helper skill может хешировать или проверять их, но никогда не копирует в эти runtime-каталоги.

## 7. Identity в git при самоизменяющемся агенте

Держи identity (SOUL, ARCHITECTURE, config, skills, hooks, plugins, cron adapters, service launchers) в git, чтобы её можно было ревьюить и восстанавливать. Агент тоже будет править её части во время работы. Двум писателям нужен протокол, иначе один молча стирает другого.

Три класса файлов: **зеркалируемые файлы** (`SOUL.md`, `ARCHITECTURE.md`, `config.yaml`) пишутся с обеих сторон; **отслеживаемые каталоги** (skills, hooks, plugins, avatars) применяются пофайлово и экспортируются обратно; **каталоги только для apply** (cron adapters, service launchers) идут только git → runtime, никогда не экспортируются, и apply их перезаписывает.

| Правило | Что оно предотвращает |
| --- | --- |
| **Identity владеет git.** Правки оператора: сначала pull (publish job сам коммитит правки агента) → edit → commit → push → деплой применяет. | Неотслеживаемый дрейф; конфликты с последним publish агента. |
| **Apply аддитивен.** Git → runtime копируется пофайлово; runtime-файлы никогда не удаляются. | Стирание skills, созданных агентом. |
| **Publish зеркалирует обратно.** Job по расписанию экспортирует runtime-правки, коммитит, делает rebase и push. Его коммиты могут пропускать CI, поэтому он сам прогоняет закреплённый secret scanner по исходящему диапазону; находка отбрасывает commit, и ничего не пушится. | Правки агента, существующие только в одном месте; непросканированные секреты на remote. |
| **Трёхсторонний маркер.** Записывай checksum последней применённой git-копии. Runtime ≠ маркер → правил агент; git ≠ маркер → правил оператор. | Гадание, кто что изменил. |
| **Отказ при изменении с обеих сторон.** Тот же файл изменён с обеих сторон после маркера → apply отказывает и называет файл. Проверка живёт в самом скрипте apply, поэтому отказывает каждый путь (прямой запуск, деплой, upgrade, publish job). Сливает человек; переключатель force существует, но это осознанное «git побеждает». | Деплой, молча откатывающий более новые правки агента. |
| **Односторонняя runtime-правка сохраняется.** Runtime-правка файла, который git не менял, остаётся на месте и публикуется в тот же тик; она не блокирует apply. | Ложные отказы, стопорящие оба направления. |
| **Закоммиченные байты — не конфликт.** Runtime-файл, точные байты которого git сам закоммитил между последним apply и текущим head, был опубликован, а затем заменён; apply перезаписывает его head-версией и ничего не теряет. Отказывают только байты, которых git никогда не коммитил. | Отказ деплоя из-за того, что уже опубликованную правку агента снова изменили в git. |
| **Маркер применённого дерева охраняет экспорт.** Записывай identity-commit, который runtime получил последним. Publish job применяет дерево, по которому git впереди, до экспорта и отказывается экспортировать, пока git всё ещё впереди, поэтому порядок pull на хосте не важен. | Повторный publish, коммитящий устаревший runtime поверх свежезапушенных файлов. |
| **Один lock на оба направления.** Publish пропускает тик, если lock держит apply; apply ждёт, затем отказывает безопасно (fail closed). | Экспорт наполовину скопированного дерева. |
| **Явный retire.** Команда retire удаляет путь из git и runtime вместе; закоммить, запушь и перезапусти apply, чтобы маркер догнал. Publish отказывается воссоздавать путь, удалённый каким-либо commit. | Вывод об удалении из отсутствия (один такой скрипт однажды стёр десятки skills). |
| **Никаких маркеров конфликта.** Publish отказывается коммитить `<<<<<<<` в файлах identity. | Маркеры, попавшие в живой config. |
| **Gate схемы config.** Apply отказывает git-версии `config.yaml`, чья версия схемы новее, чем ожидает релиз, и откладывает ту, что новее живого runtime, до upgrade image. | Config новой схемы, попавший на всё ещё работающий старый image. |
| **Seeds принадлежат runtime.** Файлы, которые git засевает один раз (например, список cron jobs), после первого apply принадлежат runtime. | Git, перезаписывающий живые расписания. |

Что **не** деплоится через git: cron jobs (меняй их через CLI на хосте; publish job копирует их обратно в seed; поле, которое CLI задать не может, например toolsets job, правится в файле jobs атомарно), память (memory tool агента или аккуратная правка на хосте), секреты (только `.env` на хосте). А поскольку config зеркалируется, runtime-команда `config set` может переключить policy-ключ, который publish затем закоммитит, — отсюда проверка при деплое из §6.

Отказ → симптом → исправление:

| Отказ | Симптом | Исправление |
| --- | --- | --- |
| Экспорт сломан (push key, грязное дерево) | Правки агента перестают появляться в git | Alert после N неудачных publish подряд (здесь пять); чини дерево, не форсируй. Восстановление job возвращает только каталог identity, никогда не делает reset всего репозитория, который выбросил бы постороннюю работу |
| Apply запущен без проверки изменений с обеих сторон | Недавние правки skills агентом исчезли | Встрой проверку в сам скрипт apply, чтобы она покрывала каждый путь |
| Удаление сделано только в git | Удалённый skill возвращается при следующем publish | Используй команду retire |
| Один и тот же ключ изменён с обеих сторон | Конфликт rebase при publish, повторяется | Слей вручную на хосте; job восстанавливает состояние и сообщает |
| Лог экспорта говорит, что git впереди runtime | Publish продолжает отказывать | Apply не прошёл: либо отказ из-за изменения с обеих сторон (слей этот файл), либо отложенная схема config (дождись upgrade) |

## 8. Доведение коррекции до каждого владельца

Коррекция («мы больше не используем X», «этот канал приватный») обычно живёт сразу у нескольких владельцев: в SOUL, ARCHITECTURE, skill, записи памяти, cron-промпте, странице заметок. Исправь всех действующих владельцев, замени устаревший текст вместо дописывания «кроме…» и проверь каждого. Исторические свидетельства не трогай. Полный контракт: [Рабочие циклы, §4](operating-loops.ru.md).

## 9. Как сообщать агенту об изменениях оператора

Когда ты меняешь то, чем агент владеет или что отслеживает (skill, который он поддерживает, задачу, которую он завёл, правило, которому он следует), сообщи ему, а не жди, пока он сам обнаружит расхождение.

- Отправь **разовую помеченную заметку оператора**: `hermes -z` принимает один промпт и печатает только ответ. Передай заметку через stdin в свою CLI-обёртку (она запускает CLI внутри контейнера от имени runtime-пользователя), чтобы ничего не пришлось экранировать:

  ```bash
  ssh <host> 'cd <ops-repo> && ./scripts/hermes-cli.sh -z "$(cat)"' < operator-note.txt
  ```

- Начни заметку с «Operator note (from <who>)», перечисли изменения и попроси коротко ответить, что агент сделал.
- Попроси агента **самостоятельно проверить каждый пункт**, прежде чем закрывать свои задачи. Хороший агент часть закроет, а часть оставит с объяснением причин; это несогласие — информация.
- Не правь память или список задач агента у него за спиной, чтобы «избавить его от хлопот».

## 10. Настройка identity для другого человека

- **Начинай с шаблонов**, а не со своего агента: [шаблон SOUL](../templates/SOUL.template.md), [шаблон ARCHITECTURE](../templates/ARCHITECTURE.template.md).
- **Свой SOUL человек пишет сам** — или агент составляет черновик по разговору с ним, а человек его утверждает. Голос твоего агента настроен под тебя.
- **Никогда не копируй свою память, профиль USER, заметки или личные skills.** Начинай с пустой памяти; она наполнится из его коррекций.
- Передавай только действительно общие skills (governance, гигиена, отладка runtime). Личные skills — в приватный overlay, если вообще куда-то.
- С первого дня задай тройку политик — `skills.write_approval: true`, `memory.write_approval: false`, `approvals.cron_mode: deny` (cron не может сам себе согласовать опасные команды) — в каждом profile, и проверяй её при каждом деплое ([справочник по сетапу, §8](setup-reference.ru.md)).
- Дай его агенту собственный каталог данных и profile. Один gateway на каталог данных.
- Добавь проверку размера (§4) и защиту от перехвата (§5) до первой настоящей сессии.

См. также: [приёмы сетапа](setup-patterns.ru.md), [hardening guide](hermes-hardening.md), [Принципы, §9](../readings/principles-from-hermes-in-practice.ru.md).
