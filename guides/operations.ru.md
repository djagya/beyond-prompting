# Долгоживущий Hermes: полевое руководство по эксплуатации

**Операционная практика одного постоянно работающего Docker-развёртывания, не официальная гарантия Hermes.** Оно описывает то, что это развёртывание запускает и проверяет; там, где поведение относится к сборке форка, которую оно использует, текст говорит «в используемой здесь сборке форка». На стоковом upstream проверь каждую проверку один раз на своей версии.

Hermes у тебя уже работает в Docker (см. [эталонный сетап](setup-reference.ru.md)). Это руководство о том, как месяцами держать его здоровым: что проверять, что означают тревожные симптомы, как обновляться и откатываться, как держать под контролем состояние, бэкапы и диск. Контроли безопасности (экспозиция, секреты, approvals, поверхность инструментов) описаны в [Hardening Hermes Agent](hermes-hardening.md); здесь на них ссылаются, а не повторяют.

Обозначения: `<container>` — имя контейнера Hermes, `<profile>` — profile (`default` для основного), `<data-dir>` — директория хоста, смонтированная как `$HERMES_HOME`, `<image>@sha256:<digest>` — закреплённый image. `hermes …` означает CLI, запущенный через твою обёртку от имени runtime-пользователя (`docker exec -u hermes <container> …`), никогда от root.

## 1. Health — ещё не работоспособность

Зелёный контейнер и `/health` доказывают, что процесс отвечает по HTTP, а не что агент может думать, добираться до своих инструментов или общаться в своих каналах. Каждый сбой ниже случился при зелёном health.

| Сбой при зелёном статусе | Почему статус остаётся зелёным | Проба |
| --- | --- | --- |
| Новый image переместил или удалил бинарник, указанный в `command:` MCP server | Server не стартует и откладывается при каждой загрузке; gateway работает без него | При каждом деплое разреши `command:` каждого включённого stdio server с PATH самого gateway (`docker exec -u hermes <container> sh -c 'command -v <cmd>'`; PATH login shell может отличаться) и роняй деплой, если одного не хватает; затем `hermes mcp test <name>` |
| `config.yaml` не распарсился при загрузке | Gateway откатывается к `.env` и defaults и продолжает работать, не отвечая ничего полезного | Ищи в логе этой загрузки (после последнего стартового баннера) предупреждение «failed to process config.yaml — falling back»; свежий `config get` его не увидит. Запускай при каждом деплое |
| Бюджет чтений secret manager израсходован при загрузке | Секреты разрешаются в пустые значения; messaging token отсутствует, платформа так и не подключается | Ищи в логе этой загрузки ошибки разрешения секретов для messaging tokens; отправь реальное сообщение и дождись, пока turn завершится. Отслеживай оставшийся бюджет в sweep |
| Закончились кредиты провайдера или истёк auth | Каждый turn завершается ошибкой; ничего не падает | Grep по логу агента (`$HERMES_HOME/logs/agent.log`) на `401`, `quota`, `rate limit`, `billing`, `insufficient`; один синтетический turn |
| Настроенный backend web search или extract больше не существует в image | Вызовы инструментов падают; больше ничего | При деплое проверяй, что имя каждого настроенного backend разрешается в работающем image |
| Supervised slot gateway лежит, хотя контейнер Up | Docker видит живой PID 1 (supervisor) | `docker exec -u hermes <container> s6-svstat /run/service/gateway-<profile>` и `curl -fsS http://127.0.0.1:<api-port>/health` |
| Два gateway опрашивают один bot token | Оба процесса здоровы; платформа делит updates между ними | Посчитай процессы gateway (`ps -eo pid,args` в контейнере) и перечисли все контейнеры, монтирующие `<data-dir>` (`docker inspect` → `.Mounts`). Симптом — ошибки «conflict» от платформы и потерянные сообщения |

Правило: **один gateway на директорию данных.** Sidecar, собранный из того же image, запускает второй gateway из service bundle образа.

## 2. Периодичность проверок

Оформи проверки как **один sweep-скрипт**, а не как сниппеты, скопированные из документа. Каждая проверка печатает одну строку `PASS|WARN|FAIL <check>: <detail>`; скрипт завершается с ненулевым кодом только при FAIL. *Ожидаемый* сбой (заведомо сломанная необязательная интеграция, credential в ожидании ротации) вносится в allowlist и печатает WARN с exit 0 — привычный красный цвет приучает людей игнорировать exit codes.

```bash
#!/usr/bin/env bash
# sweep.sh — skeleton; add one function per row
fails=0
row() { printf '%s %s: %s\n' "$1" "$2" "$3"; [ "$1" = FAIL ] && fails=$((fails+1)); }
if docker exec -u hermes <container> s6-svstat /run/service/gateway-default | grep -q '^up'
then row PASS gateway/slot up; else row FAIL gateway/slot down; fi
# disk, backup age, memory caps, MCP commands, policy keys, ... one row each
exit $(( fails > 0 ))
```

| Периодичность | Проверки |
| --- | --- |
| **Ежедневно** (2 мин) | Контейнеры Up и не в restart loop (`RunningFor` не сбрасывается); slot gateway up и `/health` отвечает; нет свежих ошибок в логе агента; ошибки auth/quota провайдера; messaging platform подключена; фоновые циклы (publish identity, sync заметок, backup) отработали и не залогировали FATAL; диск заполнен меньше чем на ~80%; supply-chain job не красная |
| **Еженедельно** (10 мин) | Дрейф identity: runtime получил последний identity-commit, publish по-прежнему доставляет правки агента, рабочее дерево на хосте чистое и синхронизировано с remote; список skills загружается без дубликатов, skills, написанные агентом, доходят до git, `name:` во frontmatter совпадает с директорией; `hermes cron list` — jobs на паузе или с ошибками и застарелые last errors (остановка автономного поведения — самый тихий дрейф); оба файла `.env` на месте с ключами, которые нужны стеку; именованные profiles по-прежнему несут закреплённые safety-ключи; файлы с владельцем root в `<data-dir>`; `user: "0:0"` и security options песочницы всё ещё в compose; images, которые можно удалить; digest дрейфа pins sidecar; сроки истечения ignore |
| **Ежемесячно** (20 мин) | Полный sweep-скрипт: файлы памяти относительно их char limits; размер `SOUL.md` / `ARCHITECTURE.md` относительно лимита context-файла и бюджета prompt; тройка install-policy, прочитанная из живого config (см. [hardening](hermes-hardening.md)); web backends разрешаются; каждая MCP command разрешается; config загружен без отката; секреты messaging разрешились в этой загрузке; бюджет secret manager; OOM kills за последние 24 ч; бинарники overlay, затеняющие бинарники image; receipts живых hotfix; jobs, которые должны оставаться на паузе, на паузе; порты всё ещё привязаны к loopback; свежесть бэкапа и последняя проверенная копия базы; запас cgroup по PIDs/memory; scratch сверх бюджета; больше images, чем живой + N-1; владелец файлов runtime; грязное дерево. Вручную: admin UI доступны с другого устройства в приватной сети, ожидающие обновления ОС и Docker, защита веток форка на месте |
| **Ежеквартально** | Учение по восстановлению в изолированный target (§6); ревью allowlists для approvals и ignore lists |

Запускай sweep со всеми строками. Режим `--quick`, пропускающий строки, — другая проверка; не засчитывай его exit 0 как ежемесячный sweep.

## 3. Красные флаги → первая реакция

| Симптом | Что это значит | Делай | Не делай |
| --- | --- | --- | --- |
| `can't start new thread`, или gateway умер около лимита PID | Лимит PID в cgroup забит остатками; перезапуск service их не освобождает | Пересоздай контейнер через deploy-скрипт; затем найди утечку (обычно браузер или вышедший из-под контроля дочерний процесс инструмента) | `s6-svc -u` gateway на месте |
| Gateway не может писать в базу (`database disk image is malformed`, `file is not a database`, `disk I/O error`) | Повреждение живого state store прямо сейчас | Останови контейнер, скопируй файлы базы, чини копию ([skill по state store](../skills/live-state-store-maintenance/SKILL.md)) | Перезапускать gateway: однажды перезапуск во время шторма записей перезаписал заголовок базы |
| Контейнер `Exited` после перезапуска Docker или containerd | Новый daemon не взвёл заново restart policy, пока старая остановка ещё шла | Запусти deploy-скрипт; проверь каждый контейнер | Рассчитывать, что `restart: unless-stopped` это покрывает |
| Агент молчит, `/health` зелёный | Auth/кредиты провайдера, отсутствующий messaging token, откат config или два gateway | Пройди таблицу из §1 сверху вниз | Первым делом пересоздавать контейнер: потеряешь boot log |
| `config.yaml` починен, агент всё ещё молчит | Gateway читает config только при загрузке | Перезапусти service gateway на месте (`s6-svc -r /run/service/gateway-default`) | Пересоздавать ради этого контейнер: это опустошает `/run/service` |
| Ядро убило процесс в контейнере по OOM | Обычно один дочерний процесс инструмента сверх лимита памяти; gateway выживает | Найди вызов инструмента в это время и исправь шаблон команды | Поднимать лимит в качестве исправления |
| Файл памяти близок к char limit или превысил его | Сверх лимита все записи всё равно загружаются, но Hermes отклоняет каждое новое добавление в память; сообщает об этом только строка в логе | Попроси агента выполнить memory hygiene и отчитаться, что куда переехало ([memory hygiene](../skills/memory-skill-boundary-hygiene/SKILL.md), [руководство по identity](identity-memory-context.ru.md)) | Править память за спиной агента или поднимать лимит в качестве исправления |
| Диск заполняется | Images, snapshots, scratch, логи или session store | Классифицируй перед удалением (§8) | `rm -rf` всего, что называется `cache`, или любого worktree |
| Контейнер в restart loop | Проблема с владельцем файлов/пользователем entrypoint или boot check спотыкается о файл в директории данных | `docker logs --tail 200 <container>`; исправь то, что называет шаг загрузки | Убирать security options, пока контейнер не загрузится |
| Фоновая job «успешна», но ничего не меняется | Застряла из-за грязного дерева, lock или отклонённого конфликта | Поищи в её логе `refusing`/`conflict`/«git is ahead of the runtime»; разреши вручную | По умолчанию форсировать одну из сторон |
| Postcheck обновления падает на истёкшем внешнем токене после здорового cutover | Мёртвый credential, а не плохой image | Ротируй credential; заверши проверки приёмки вручную | Откатываться |

## 4. Runbook обновления (установки из image)

`hermes update` отказывается работать на установках, управляемых через image; обновление — это замена image. Группируй изменения так, чтобы одно окно обходилось одним пересозданием. Перед началом запиши commit ops-репозитория, на котором стоит хост: откат делает его checkout.

1. **Выбери target.** Конкретный релиз, закреплённый по digest (`<image>@sha256:<digest>`), никогда не `latest`.
2. **Прочитай release notes** и сравни поставляемый default config. Ищи **переименованные или удалённые ключи**: переименованный ключ молча игнорируется, а image может переписать настройку топологии на своё новое значение по умолчанию. По каждому удалённому ключу решай осознанно; затем проверь, какой ключ на самом деле читает работающий image (`hermes config get <key>` после загрузки). Запиши версию схемы config (`_config_version`), на которую мигрирует новый image: от неё зависит, как работает откат.
3. **Закрепи и запиши доказательства.** Закоммить новый digest и release manifest вместе с SBOM образа (§7). Повышение схемы git config относится к тому же commit; до него apply отказывается принимать более новую схему.
4. **Сначала сделай обслуживание хранилища в отдельном окне.** Compaction полнотекстового индекса или подобная работа над session store имеет собственный откат и выполняется при остановленных писателях. Никогда не совмещай её с обновлением.
5. **Предусловия.** Бюджет чтений secret manager не израсходован (пересозданный gateway при загрузке забирает каждый секрет; deploy-скрипт отказывает). Дождись простоя: живая сессия может идти часами, и перезапуск под ней теряет turn. В detached-режиме опрашивай условие «нет активности агента, инструментов или cron N минут».
6. **Предварительное затишье.** Один раз запусти publish identity, чтобы ни одна правка агента не осталась неэкспортированной. Поставь на паузу циклы на хосте (publish job, таймер бэкапа). Поставь агента на паузу (`hermes pause`), дай текущим turns завершиться, убедись, что на task board ничего не выполняется, и останови supervised writers, которые ты добавил сам.
7. **Заморозь ingress, затем snapshot — отдельным шагом.** Останови входящий трафик чата, затем консистентно скопируй каждый SQLite-файл (основной и per-profile session stores, task boards, историю cron) и дерево данных и проверь копии (`quick_check` через SQLite образа). Сначала проверь свободное место: размер дерева + 3× базы + живой WAL, плюс 2× новый image для pull. **Не** связывай `snapshot && upgrade`: сначала прочитай результат snapshot.
8. **Останови web UI.** Он не должен работать с наполовину мигрированной базой.
9. **Сними флаг паузы перед обновлением.** Healthcheck образа падает, пока флаг существует, поэтому контейнер никогда не стал бы healthy. Держи заморозку за счёт удержанного ingress и циклов на паузе.
10. **Обнови** через deploy-скрипт (pull закреплённого digest, пересоздание). Скрипт сначала сохраняет логи старого контейнера (единственная запись крашей и OOM до обновления) и проставляет safety-ключи в каждый profile до первой новой загрузки. Первая загрузка может выполнять долгие миграции индексов; длинный `start_period` healthcheck держит контейнер в `starting`. Не делай `compose up` повторно посреди миграции. Если ты останавливал gateway через `hermes gateway stop`, он остаётся остановленным и после пересоздания; иначе boot reconciler перезапускает gateways, которые работали.
11. **Проверь** (таблица из §1, затем сделай один evidence-скрипт планкой готовности):

    ```bash
    docker inspect -f '{{.Image}}' <container>          # running image id
    docker image inspect -f '{{.Id}}' <image>@sha256:<digest>   # must match
    hermes --version
    grep -m1 '^_config_version' <data-dir>/config.yaml  # equals the image's schema
    hermes config check
    hermes doctor
    hermes mcp list && hermes mcp test <each-server>
    ```

    Также: размер WAL стабилен, `quick_check` ok (на многогигабайтной базе живую проверку пропусти; целостность покрывают копии snapshot), в логе этой загрузки нет ошибок забора секретов для messaging tokens, щиты policy и profiles заново подтверждены. Затем один реальный turn в чате, один canary запланированной job и одно чтение через MCP.
12. **Возобновляй по порядку.** Заново подключи supervised services (`/run/service` не переживает пересоздание: boot reconciler пересобирает gateway slots, всё, что ты подключил сам, пропадает) → сними паузу → верни publish job → верни ingress → запусти web UI → таймер бэкапа, с первым бэкапом после обновления уже после «go».
13. **Принимай** в два этапа: короткая валидация, пока ingress и фоновые циклы ещё на паузе, затем явное «go», затем разморозка. Записи в базу после миграции нельзя перенести назад.

### Откат

Повторное закрепление старого digest — **не** откат, если новый image уже мигрировал `config.yaml` или базу состояния: старый image откроет новые индексы и triggers.

1. Сделай на хосте checkout записанного commit ops-репозитория до обновления (pin в compose и release manifest откатываются вместе; нужно чистое дерево) или проведи отревьюенный pin bump обратно на предыдущий image.
2. Если новый image мигрировал config или базы, останови контейнер и сначала восстанови snapshot, сделанный до обновления: копии базы, **удалив живые файлы `-wal` и `-shm`** перед их размещением (восстановленная база рядом с оставшимся WAL открывается в несогласованном состоянии), затем дерево данных (skills, profiles, память) и бэкапы `config.yaml` и `.env` с timestamp.
3. Запусти путь обновления из откаченного дерева, только gateway. Заново подключи supervised services, запусти web UI, проверь, как описано выше.

Всё, что произошло после snapshot, теряется. Храни N-1 image, пока новый не проработает полные сутки. `docker image prune` (только dangling) оставляет image, закреплённый по digest; `docker image prune -a` удаляет каждый image, не используемый ни одним контейнером, включая N-1, — не запускай его.

### Окно обслуживания ОС хоста

Всё, что перезапускает Docker (обновления пакетов хоста, затрагивающие `docker`/`containerd`, перезагрузка) или пересоздаёт Hermes, относится к такому же окну:

- Сначала проверь бюджет secret manager и дождись простоя, как описано выше.
- Запускай обновления пакетов **detached, как root systemd unit с логом**: перезапуск пакета VPN или SSH обрывает твою сессию посреди процесса.

  ```bash
  sudo systemd-run --unit=host-upgrade -p StandardOutput=append:/var/log/host-upgrade.log \
    -p StandardError=append:/var/log/host-upgrade.log \
    /usr/bin/env DEBIAN_FRONTEND=noninteractive apt-get -y upgrade
  sudo tail -f /var/log/host-upgrade.log
  ```

- **Любой перезапуск Docker может оставить Hermes остановленным.** Когда containerd и Docker обновляются вместе, старый daemon может зависнуть на остановке, а новый снимает restart policy, пока медленная остановка ещё идёт; после этого контейнер остаётся `Exited` и после последующих перезагрузок. **После этого всегда запускай deploy-скрипт**, затем `docker ps -a`, чтобы найти всё в состоянии `Exited`.
- Перезагрузись, если хост об этом просит.
- Другие долгие шаги (snapshot, обновление) тоже запускай detached (`nohup … > <log>`) и читай лог; никогда не связывай их через `&&` за SSH-сессией.
- Часы или часовые пояса хоста и контейнера могут различаться; привязывай циклы ожидания и поиск по логам к UTC.

## 5. Уход за state store

Session store (SQLite с WAL и полнотекстовыми индексами) — самое хрупкое состояние, которым ты владеешь. Процедура — в [live-state-store-maintenance](../skills/live-state-store-maintenance/SKILL.md); правила:

- **Чистая остановка — предусловие.** Stop grace (compose `stop_grace_period`, s6-overlay `S6_SERVICES_GRACETIME`/`S6_KILL_GRACETIME`) должен превышать время drain gateway. Нечистый выход может пометить поисковый индекс устаревшим, и следующая загрузка перестроит его поверх живых записей.
- **Никакой перестройки индекса под живыми писателями.** Полнотекстовая перестройка наперегонки с активными сессиями была повторяющимся триггером повреждений. В используемой здесь сборке форка путь живой перестройки отключён, а записи в индекс при сбое не блокируют работу (fail open).
- **Никогда не открывай живой WAL через `sqlite3` хоста.** Используй SQLite самого image (его Python) в одноразовом контейнере или работай с копией.
- **Stop → copy → repair.** Если канонические таблицы ещё читаются, спасение живого файла обычно сохраняет больше истории, чем восстановление последнего snapshot.
- **Рост идёт от дубликатов compaction, а не от возраста.** Context compaction заново сохраняет вывод инструментов; pruning по возрасту освобождает мало. Это развёртывание выключает auto-prune сессий (транскрипты — это и есть история) и освобождает место в отдельном окне compaction индекса при остановленных писателях. Если когда-нибудь будешь удалять, сначала архивируй и проверь, что каждый id архивированного сообщения разрешается.
- **Держи fixtures и эксперименты вне data home.** Намеренно повреждённые тестовые базы сломали snapshot и отправили в crash loop новый image, чей boot check открывает каждый SQLite-файл в этой директории; экспериментальные базы раздували каждый snapshot на десятки GB.
- **Повторяющиеся повреждения при чистых остановках и без живых перестроек:** прогони ночной тест оперативной памяти, прежде чем винить софт.
- **Никакого watchdog для gateway.** Restarter на хосте, который убивал gateway через SIGKILL, молча оживлял повторяющийся сбой и перезапустил намеренно остановленный контейнер посреди ремонта, был удалён. Принятый компромисс: gateway, оставленный в состоянии wanted-down внутри работающего контейнера, никто не поднимет, потому что restart policy Docker срабатывает только при выходе контейнера. Обнаружение — ежедневная проверка и замолчавший агент; восстановление — вручную.

## 6. Бэкапы, которые восстанавливаются

«Бэкап прошёл» — ещё не «бэкап восстанавливается».

- **Готовь проверенную копию.** Копируй каждую базу через backup API SQLite внутри image (одноразовый вспомогательный контейнер из того же digest с явным entrypoint, чтобы он не запустил второй gateway), размещай копию вне bind mount данных, выполни `PRAGMA quick_check` на подготовленной копии и только потом помечай её как хорошую. Никогда не помечай непроверенную копию как хорошую: однажды помеченная копия оказалась повреждённой.
- **Canary-строка в sweep:** возраст последнего бэкапа, последняя проверенная копия базы и отсутствие FATAL в логе бэкапа. Запуск, наткнувшийся на нечитаемые файлы, — это WARN, а не PASS.
- **Exclude lists нужен тест.** Логи, кэши пакетов, snapshots, scratch, worktrees и установленные зависимости исключены; credentials, память, сессии, токены и проверенная копия базы включены. Тест проверяет оба списка, чтобы рефакторинг не мог незаметно выкинуть путь.
- **Пароль и ключи репозитория бэкапов держи на хосте**, не монтируя их в контейнер агента, чтобы агент не мог удалить собственные бэкапы (контроли: [hardening](hermes-hardening.md)). Ночная job печатает только dry-run удаления; настоящий prune — действие оператора.
- **Еженедельная структурная проверка** репозитория и **ежеквартальное учение:** восстанови известный файл и базу в изолированный target (никогда не в живой home), открой её и прогони проверки приёмки. Если не получается, бэкап — это театр.

## 7. Supply chain и дисциплина релизов форка

Policy и контроли — в [hardening](hermes-hardening.md); здесь рабочий цикл:

- **Digest pin — точка ревью, а не фид уязвимостей.** Коммить SBOM (например, Syft или Trivy CycloneDX) на каждый pin, в том же commit, что и pin, и ежедневно пересканируй закоммиченные SBOM по актуальной базе advisories, не делая pull images. Advisories для свежего image часто появляются через несколько часов после публикации. Деплой отказывает pin, у которого нет файла SBOM.
- **Pins двигаются только одним путём:** скрипт bump → ревью diff человеком → SBOM → один commit → деплой. Никаких автоматических PR с обновлением images: они воевали бы с release manifest.
- **Дрейф:** плавающие tags sidecar — еженедельный digest, а не тревога. Для image Hermes более новый релиз, сдвинутая release branch или сдвинутый digest в registry роняют watch.
- **Admission:** новые images, базы Dockerfile и CI actions должны быть в allowlist; actions остаются закреплёнными на полный commit SHA.
- **Ignores — это строки, а не покрывала:** одна строка `(advisory, image)` с причиной и сроком истечения не больше примерно месяца. Находка, которую исправляет pin bump, — это bump, а не ignore. Неисправимые находки считаются одним предупреждением на image.
- **Блокируй, а не только сообщай.** Сканер в режиме report-only неделями работал с критическими находками, которые никто не читал.
- Выбирая исправленную версию зависимости, соблюдай правило минимального возраста релиза в своём registry.

Если ты используешь собственный image форка:

- Выводи версию из ближайшего upstream release tag; роняй сборку, если имя release branch не называет ни эту версию, ни её major.minor. Sync, который сдвигает базу, создаёт новую release branch.
- Зафиксируй scope до первой сборки; прогоняй gate на объединённом head один раз; подтверди, что смёрженное дерево совпадает с проверенным; отменяй сборки для устаревших heads. Pin должен указывать на head release branch.
- Мёржи fork `main` в release branch *до* сборки, чтобы tracking PR не требовал второй сборки. Если `main` всё же сдвинулся после сборки, открывай tracking PR из побочной ветки (head релиза плюс merge `main`, то же дерево), а не двигай release branch.
- Публикуй ровно тот image, который тестировал, — без пересборки между тестом и публикацией.
- Никогда не делай rebase или force-push release branches; мёржи release → `main` через merge commit.
- Перед push в release branch запусти локально собственные jobs release workflow, прочитанные из файла workflow. Каждому gate нужен негативный контроль: докажи, что он падает на заведомо плохом head. Локальный gate, который передавал свой скрипт через `ssh … bash -s`, месяцами сообщал PASS, потому что stdin съедал дочерний процесс.

## 8. Гигиена диска и scratch

- **Классифицируй перед удалением.** Директория с именем `cache` может содержать веса моделей, необработанные голосовые сообщения, состояние skills или единственную копию почты. Кэши пакетных менеджеров удаляй по имени; остальное не трогай, пока не классифицирован каждый дочерний элемент.
- **Никогда не делай `rm -rf` git worktree** или директории внутри него: это удаляет tracked files. Используй `git worktree remove` на чистом дереве (ветка сохранится). Если worktree зарегистрирован изнутри контейнера, запускай git там, от runtime-пользователя.
- **Временный scratch с владельцем:** у временных snapshots, репетиционных копий и scratch-деревьев есть владелец, цель и срок окончания; закрывай их в той же задаче. Дай sweep бюджет в байтах на каждый scratch root.
- **Images:** храни живой + N-1 (и то же для любого версионированного source volume UI). Остановленный оставшийся контейнер блокирует `docker rmi`. JSON-логи контейнеров и логи cron хоста по умолчанию не ограничены; добавь ротацию.
- **Сканам агента нужны потоковое чтение и лимиты памяти.** Поиск, читавший каждый файл целиком, наткнулся на многогигабайтную базу и был убит OOM. Научи агента (текстом skill) читать потоково и пропускать базы; где возможно, ограничивай память на команду.
- Держи браузеры вне cgroup gateway; подбирай `pids`, `nofile` и `shm` под то, что осталось.

## 9. Алерты

- Направляй ops- и supply-chain-алерты в **канал, до которого агент не может дотянуться и который не может заглушить** (отдельный бот, отдельный чат или email). Скомпрометированный агент не должен иметь возможности выключить собственную тревогу.
- **Circuit breakers на фоновых циклах:** поднимай тревогу после N последовательных сбоев. Однажды publish loop молча лежал несколько часов.
- **Тестируй путь алерта end to end.** Алерт несколько дней падал с «chat not found».
- **Потерянный алерт — не зелёный статус.** Если отправка алерта не удалась, job сохраняет свой код ошибки, а в остальном чистый запуск тоже завершается с ненулевым кодом.
- **Ignores истекают.** Ignore без срока — постоянная слепая зона.

## 10. Проектирование состояний сбоя

Для каждого самоуправляемого компонента (browser slots, фоновые циклы, sync jobs):

- Раздели сбои на **auto-recover** (инфраструктурный класс: потерянный supervisor, перезапуск, зависание — восстанавливаться после короткого grace-окна) и **needs-human** (auth, policy, конфликтующие правки).
- **Поднимай тревогу по всему, что застряло дольше ~30 минут**, независимо от класса.
- **Сохраняй историю сбоев** вне контейнера. Логи умирают при пересоздании; следующему расследованию нужны timestamps.
- Текст ошибки — это UX для агента: 403 с пометкой «permission-blocked» заставил агента часами повторять попытки. Говори, что делать дальше и когда остановиться.

Правила для cron и циклов (расписание, toolsets, approvals) — в [runtime-automation-governance](../skills/runtime-automation-governance/SKILL.md).

## 11. Цикл обучения

Закрывай каждое окно обслуживания, обновление или инцидент одними и теми же четырьмя шагами:

1. **Сначала закодируй исправления** в скрипты, строки sweep, тесты или guards для config. Фраза «не забыть…» — последнее средство.
2. **Обнови канонический документ**: у каждого факта один дом. Не пиши живое состояние в прозу: pins, digests, id jobs или «до <date>» устаревают за день; указывай на файл или команду, которые их доказывают.
3. **Напиши датированную неизменяемую ретроспективу** — это входные данные, а не канон — и в том же изменении перенеси её долговечные пункты в их дома.
4. **Найди устаревшие документы**, которые противоречат только что выученному.

Недельная версия этого цикла по реальным сессиям — [извлечение уроков за неделю](weekly-learning-extraction.ru.md). Если развёртывание за тебя обслуживает coding agent, его правила — в [руководстве оператора для coding agent](coding-agent-operator.ru.md).
