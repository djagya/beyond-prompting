# Долгоживущий Hermes: полевое руководство по эксплуатации

**Операционная практика одного постоянно работающего Docker-развёртывания, не официальная гарантия Hermes.** Пунктов с пометкой *проверь на своей версии* нет в текущей документации Hermes.

Hermes у тебя уже работает в Docker (см. [эталонный сетап](setup-reference.ru.md)). Это руководство о том, как месяцами держать его здоровым: что проверять, что означают тревожные симптомы, как обновляться и откатываться, как держать под контролем состояние, бэкапы и диск. Контроли безопасности (экспозиция, секреты, approvals, поверхность инструментов) описаны в [Hardening Hermes Agent](hermes-hardening.md); здесь на них ссылаются, а не повторяют.

Обозначения: `<container>` — имя контейнера Hermes, `<profile>` — profile (`default` для основного), `<data-dir>` — директория хоста, смонтированная как `$HERMES_HOME`, `<image>@sha256:<digest>` — закреплённый image.

## 1. Health — ещё не работоспособность

Зелёный контейнер и `/health` доказывают, что процесс отвечает по HTTP, а не что агент может думать, добираться до своих инструментов или общаться в своих каналах. Каждый сбой ниже случился при зелёном health.

| Сбой при зелёном статусе | Почему статус остаётся зелёным | Проба |
| --- | --- | --- |
| Новый image переместил или удалил бинарник, указанный в `command:` MCP server | Server не стартует и откладывается; gateway работает без него | Для каждого включённого stdio server разреши `command:` с PATH самого gateway (`docker exec -u hermes <container> sh -c 'command -v <cmd>'`; PATH login shell может отличаться), затем `hermes mcp test <name>` |
| `config.yaml` не распарсился при загрузке | Gateway откатывается к defaults и продолжает работать | Прочитай лог этой загрузки на ошибки загрузки config (`hermes logs errors --since 1h`). Держи одно намеренно нестандартное значение как canary и после каждой загрузки подтверждай, что gateway ведёт себя соответственно |
| Бюджет чтений secret manager израсходован при загрузке | Секреты разрешаются в пустые значения; messaging token отсутствует, платформа так и не подключается | Поищи в логе этой загрузки ошибки разрешения секретов; отправь реальное сообщение и дождись, пока turn завершится. Отслеживай оставшийся бюджет в sweep |
| Закончились кредиты провайдера или истёк auth | Каждый turn завершается ошибкой; ничего не падает | `hermes logs errors --since 1h` и grep по `401`, `quota`, `billing`, `insufficient`; один синтетический turn |
| Supervised slot gateway лежит, хотя контейнер Up | Docker видит живой PID 1 (supervisor) | `docker exec <container> /command/s6-svstat /run/service/gateway-<profile>` и `curl -fsS http://127.0.0.1:<api-port>/health` (API server должен быть включён) |
| Два gateway опрашивают один bot token | Оба процесса здоровы; платформа делит updates между ними | Посчитай процессы gateway (`ps -eo pid,args` в контейнере) и перечисли все контейнеры, монтирующие `<data-dir>` (`docker inspect` → `.Mounts`). Симптом — ошибки «conflict» от платформы и потерянные сообщения |

Правило: **один gateway на директорию данных.** Sidecar, собранный из того же image, может запустить второй gateway из service bundle образа.

## 2. Периодичность проверок

Оформи проверки как **один sweep-скрипт**, а не как сниппеты, скопированные из документа. Каждая проверка печатает одну строку `PASS|WARN|FAIL <check>: <detail>`; скрипт завершается с ненулевым кодом только при FAIL. *Ожидаемый* сбой (заведомо сломанная необязательная интеграция, credential в ожидании ротации) вносится в allowlist и печатает WARN с exit 0 — привычный красный цвет приучает людей игнорировать exit codes.

```bash
#!/usr/bin/env bash
# sweep.sh — skeleton; add one function per row
fails=0
row() { printf '%s %s: %s\n' "$1" "$2" "$3"; [ "$1" = FAIL ] && fails=$((fails+1)); }
if docker exec <container> /command/s6-svstat /run/service/gateway-default | grep -q '^up'
then row PASS gateway/slot up; else row FAIL gateway/slot down; fi
# disk, backup age, memory caps, MCP commands, policy keys, ... one row each
exit $(( fails > 0 ))
```

| Периодичность | Проверки |
| --- | --- |
| **Ежедневно** (2 мин, в идеале автоматически) | Контейнеры Up и не в restart loop (`RunningFor` не сбрасывается); slot gateway up; свежие ошибки в `hermes logs errors`; ошибки auth/quota провайдера; messaging platform подключена; фоновые циклы (sync, backup, publish) отработали и не залогировали FATAL; диск заполнен меньше чем на ~80%; supply-chain job не красная |
| **Еженедельно** (10 мин) | `hermes cron list` — jobs на паузе или с ошибками и застарелые last errors (остановка автономного поведения — самый тихий дрейф); список skills загружается без дубликатов; дрейф между каноническим источником и runtime; файлы с владельцем root в `<data-dir>`; images, которые можно удалить; сроки истечения alert-ignore |
| **Ежемесячно** (20 мин) | Полный sweep: файлы памяти относительно их char limits; размер `SOUL.md` относительно лимита в prompt; ключи policy для approvals и cron, прочитанные из живого config (см. [hardening](hermes-hardening.md)); каждая MCP command разрешается; порты всё ещё привязаны к loopback; свежесть бэкапа и последний проверенный canary; запас cgroup по PIDs/memory; ожидающие обновления ОС и Docker |
| **Ежеквартально** | Учение по восстановлению в изолированный target (§6); ревью allowlists для approvals и ignore lists |

Запускай sweep со всеми строками. Режим `--quick`, пропускающий строки, — другая проверка; не засчитывай его exit 0 как ежемесячный sweep.

## 3. Красные флаги → первая реакция

| Симптом | Что это значит | Делай | Не делай |
| --- | --- | --- | --- |
| `can't start new thread`, или gateway умер около лимита PID | Лимит PID в cgroup забит остатками; перезапуск service их не освобождает | Пересоздай контейнер через deploy-скрипт; затем найди утечку (обычно браузер или вышедший из-под контроля дочерний процесс инструмента) | Перезапускать s6 service на месте |
| Gateway не может писать в базу (`database disk image is malformed`, `file is not a database`, `disk I/O error`) | Повреждение живого state store прямо сейчас | Останови контейнер, скопируй файлы базы, чини копию ([skill по state store](../skills/live-state-store-maintenance/SKILL.md)) | Перезапускать gateway: однажды перезапуск во время шторма записей перезаписал заголовок базы |
| Контейнер `Exited` после перезапуска Docker или containerd | Новый daemon не взвёл заново restart policy, пока старая остановка ещё шла | Запусти deploy-скрипт; проверь каждый контейнер | Рассчитывать, что `restart: unless-stopped` это покрывает |
| Агент молчит, `/health` зелёный | Auth/кредиты провайдера, отсутствующий messaging token или два gateway | Пройди таблицу из §1 сверху вниз | Первым делом пересоздавать контейнер: потеряешь boot log |
| Файл памяти близок к char limit | Hermes молча обрезает память сверх лимита | Попроси агента выполнить memory hygiene и отчитаться, что куда переехало ([memory hygiene](../skills/memory-skill-boundary-hygiene/SKILL.md), [руководство по identity](identity-memory-context.ru.md)) | Править память за спиной агента или поднимать лимит в качестве исправления |
| Диск заполняется | Images, snapshots, scratch, логи или session store | Классифицируй перед удалением (§8) | `rm -rf` всего, что называется `cache`, или любого worktree |
| Контейнер в restart loop | Проблема с владельцем файлов/пользователем entrypoint или boot check спотыкается о файл в директории данных | `docker logs --tail 200 <container>`; исправь то, что называет шаг загрузки | Убирать security options, пока контейнер не загрузится |
| Фоновая job «успешна», но ничего не меняется | Застряла из-за грязного дерева, lock или отклонённого конфликта | Поищи в её логе `refusing`/`conflict`; разреши вручную | По умолчанию форсировать одну из сторон |
| Postcheck обновления падает на истёкшем внешнем токене после здорового cutover | Мёртвый credential, а не плохой image | Ротируй credential; заверши проверки приёмки вручную | Откатываться |

## 4. Runbook обновления (установки из image)

`hermes update` отказывается работать на установках, управляемых через image (задокументировано); обновление — это замена image. Группируй изменения так, чтобы одно окно обходилось одним пересозданием.

1. **Выбери target.** Конкретный release tag, закреплённый по digest (`<image>@sha256:<digest>`), никогда не `latest`.
2. **Прочитай release notes** и сравни поставляемый default config. Ищи **переименованные или удалённые ключи**: переименованный ключ молча игнорируется, а image может переписать настройку топологии на своё новое значение по умолчанию. По каждому удалённому ключу решай осознанно; затем проверь, какой ключ на самом деле читает работающий image (`hermes config get <key>` после загрузки).
3. **Закрепи и запиши доказательства.** Закоммить новый digest вместе с его SBOM (§7). Запиши digest, который заменяешь, — это твой N-1.
4. **Дождись простоя, затем заморозь.** Живая сессия может идти часами; перезапуск под ней теряет turn. В detached-режиме опрашивай условие «нет активности агента, инструментов или cron N минут» (например, `hermes logs --since 5m`). Затем поставь на паузу циклы на хосте (sync, таймеры бэкапа) и входящий трафик чата.
5. **Snapshot — отдельным шагом**, после простоя, чтобы он был свежим. Консистентно скопируй каждый SQLite-файл и дерево данных, проверь копии (`quick_check` через SQLite образа) и прочитай результат. **Не** связывай `snapshot && upgrade`: отказ внутри цепочки теряется в длинном логе.
6. **Сохрани логи старого контейнера** перед пересозданием: `docker logs <container> > <log-dir>/<container>-$(date -u +%Y%m%dT%H%MZ).log 2>&1`. Это единственная запись крашей и OOM до обновления.
7. **Обнови** через deploy-скрипт (pull закреплённого digest, пересоздание). Если ты останавливал gateway через `hermes gateway stop`, он остаётся остановленным и после пересоздания (задокументировано); запусти его явно.
8. **Перерегистрируй сервисы с внешним supervision.** `/run/service` — runtime state, которое не переживает пересоздание (в нашем развёртывании это tmpfs; проверь у себя): boot reconciler пересобирает per-profile gateway slots (задокументировано), но всё, что ты подключил туда сам, пропадает. Пусть deploy-скрипт заново создаёт ссылки и проверяет их.
9. **Проверь** (таблица из §1, затем):

   ```bash
   docker inspect -f '{{.Image}}' <container>          # running image id
   docker image inspect -f '{{.Id}}' <image>@sha256:<digest>   # must match
   hermes --version
   hermes config check
   hermes doctor
   hermes mcp list && hermes mcp test <each-server>
   ```

   Затем один реальный turn в чате, один canary запланированной job и одно чтение через MCP. Запиши версию схемы config, на которую мигрировал image (в свежих сборках наблюдается как `_config_version` в `config.yaml`; проверь на своей версии), — от неё зависит, как работает откат.
10. **Принимай** в два этапа: короткая валидация, пока ingress и фоновые циклы ещё на паузе, затем явное «go», затем разморозка.

### Откат

Повторное закрепление старого digest — **не** откат, если новый image уже мигрировал `config.yaml` или базу состояния: старый image откроет новые индексы и triggers.

1. Останови контейнер.
2. Восстанови snapshot, сделанный до обновления: сначала копии базы, **удалив живые файлы `-wal` и `-shm`** перед их размещением (восстановленная база рядом с оставшимся WAL открывается в несогласованном состоянии), затем config, `.env`, skills и память из того же snapshot.
3. Закрепи N-1 digest и задеплой заново. Перерегистрируй внешние сервисы. Проверь, как описано выше.

Всё, что произошло после snapshot, теряется. Храни N-1 image, пока новый не проработает сутки. `docker image prune` (только dangling) оставляет image, закреплённый по digest; `docker image prune -a` удаляет каждый image, не используемый ни одним контейнером, включая N-1.

### Окно обслуживания ОС хоста

Всё, что перезапускает Docker (обновления пакетов хоста, затрагивающие `docker`/`containerd`, перезагрузка), относится к такому же окну:

- Запускай обновления пакетов **detached, как root systemd unit с логом**: перезапуск пакета VPN или SSH обрывает твою сессию посреди процесса.

  ```bash
  sudo systemd-run --unit=host-upgrade -p StandardOutput=append:/var/log/host-upgrade.log \
    -p StandardError=append:/var/log/host-upgrade.log \
    /usr/bin/env DEBIAN_FRONTEND=noninteractive apt-get -y upgrade
  sudo tail -f /var/log/host-upgrade.log
  ```

- **После этого всегда запускай deploy-скрипт**, затем `docker ps -a`, чтобы найти всё в состоянии `Exited`.
- Часы или часовые пояса хоста и контейнера могут различаться; привязывай циклы ожидания и поиск по логам к UTC.

## 5. Уход за state store

Session store (SQLite с WAL и полнотекстовыми индексами) — самое хрупкое состояние, которым ты владеешь. Процедура — в [live-state-store-maintenance](../skills/live-state-store-maintenance/SKILL.md); правила:

- **Чистая остановка — предусловие.** Stop grace (compose `stop_grace_period`, s6-overlay `S6_SERVICES_GRACETIME`/`S6_KILL_GRACETIME`) должен превышать время drain gateway. Нечистый выход может пометить поисковый индекс устаревшим, и следующая загрузка перестроит его поверх живых записей.
- **Никакой перестройки индекса под живыми писателями.** Полнотекстовая перестройка наперегонки с активными сессиями была повторяющимся триггером повреждений.
- **Никогда не открывай живой WAL через `sqlite3` хоста.** Используй SQLite самого image (его Python) в одноразовом контейнере или работай с копией.
- **Stop → copy → repair.** Если канонические таблицы ещё читаются, спасение живого файла обычно сохраняет больше истории, чем восстановление последнего snapshot.
- **Рост идёт от дубликатов compaction, а не от возраста.** Context compaction заново сохраняет вывод инструментов; pruning по возрасту освобождает мало. Сначала архивируй, проверь, что каждый id архивированного сообщения разрешается, затем удаляй. Встроенный auto-prune (`sessions.auto_prune`) в текущей документации включён по умолчанию и не имеет шага архивирования; выключи его, если тебе нужна история.
- **Держи fixtures и эксперименты вне data home.** Намеренно повреждённые тестовые базы сломали snapshot и отправили в crash loop новый image, чей boot check открывает каждый SQLite-файл в этой директории; экспериментальные базы раздували каждый snapshot на десятки GB.
- **Повторяющиеся повреждения при чистых остановках и без живых перестроек:** прогони ночной тест оперативной памяти, прежде чем винить софт.
- **Watchdogs:** restarter, который убивает gateway через SIGKILL или поднимает намеренно остановленный контейнер, — источник повреждений. Он обязан уважать намеренную остановку и алертить, а не молча «лечить».

## 6. Бэкапы, которые восстанавливаются

«Бэкап прошёл» — ещё не «бэкап восстанавливается».

- **Готовь проверенную копию.** Копируй каждую базу через backup API SQLite внутри image, выполни `PRAGMA quick_check` на подготовленной копии и только потом помечай её как хорошую. Никогда не помечай непроверенную копию как хорошую: однажды помеченная копия оказалась повреждённой.
- **Canary-строка в sweep:** возраст последнего бэкапа, последняя проверенная копия базы и отсутствие FATAL в логе бэкапа.
- **Exclude lists нужен тест.** Логи, кэши пакетов, snapshots, scratch, worktrees и установленные зависимости исключены; credentials, память, сессии, токены и проверенная копия базы включены. Тест проверяет оба списка, чтобы рефакторинг не мог незаметно выкинуть путь.
- **Пароль и ключи репозитория бэкапов держи на хосте**, не монтируя их в контейнер агента, чтобы агент не мог удалить собственные бэкапы (контроли: [hardening](hermes-hardening.md)).
- **Ежеквартальное учение:** восстанови известный файл и базу в изолированный target (никогда не в живой home: `hermes import` перезаписывает свой target), открой её и прогони проверки приёмки. Если не получается, бэкап — это театр.

## 7. Supply chain и дисциплина релизов форка

Policy и контроли — в [hardening](hermes-hardening.md); здесь рабочий цикл:

- **Digest pin — точка ревью, а не фид уязвимостей.** Коммить SBOM (например, Syft CycloneDX) на каждый pin и ежедневно пересканируй закоммиченные SBOM по актуальной базе advisories (например, Grype или Trivy). Advisories для свежего image часто появляются через несколько часов после публикации.
- **Admission:** новые images и CI actions должны быть в allowlist. У каждой записи ignore есть причина и срок истечения.
- **Блокируй, а не только сообщай.** Сканер в режиме report-only неделями работал с критическими находками, которые никто не читал.
- Выбирая исправленную версию зависимости, соблюдай правило минимального возраста релиза в своём registry.

Если ты используешь собственный image форка:

- Выводи версию из upstream tag; роняй сборку, если имя release branch и версия не совпадают.
- Зафиксируй scope до первой сборки; прогоняй gate на объединённом head один раз; подтверди, что смёрженное дерево совпадает с проверенным; отменяй сборки для устаревших heads.
- Мёржи fork `main` в release branch *до* сборки, чтобы tracking PR не требовал второй сборки.
- Публикуй ровно тот image, который тестировал, — без пересборки между тестом и публикацией.
- Никогда не делай rebase или force-push release branches; мёржи release → `main` через merge commit.
- Каждому gate нужен негативный контроль: докажи, что он падает на заведомо плохом head. Локальный gate, который передавал свой скрипт через `ssh … bash -s`, месяцами сообщал PASS, потому что stdin съедал дочерний процесс.

## 8. Гигиена диска и scratch

- **Классифицируй перед удалением.** Директория с именем `cache` может содержать веса моделей, необработанные голосовые сообщения, состояние skills или единственную копию почты. Кэши пакетных менеджеров удаляй по имени; остальное не трогай, пока не классифицирован каждый дочерний элемент.
- **Никогда не делай `rm -rf` git worktree** или директории внутри него: это удаляет tracked files. Используй `git worktree remove` на чистом дереве (ветка сохранится). Если worktree зарегистрирован изнутри контейнера, запускай git там, от runtime-пользователя.
- **Временный scratch с владельцем:** у временных snapshots, репетиционных копий и scratch-деревьев есть владелец, цель и срок окончания; закрывай их в той же задаче. Дай sweep бюджет в байтах на каждый scratch root.
- **Images:** храни живой + N-1. JSON-логи контейнеров и логи cron хоста по умолчанию не ограничены; добавь ротацию.
- **Сканам агента нужны потоковое чтение и лимиты памяти.** Поиск, читавший каждый файл целиком, наткнулся на многогигабайтную базу и был убит OOM. Научи агента (текстом skill) читать потоково и пропускать базы; где возможно, ограничивай память на команду.
- Держи браузеры вне cgroup gateway; подбирай `pids`, `nofile` и `shm` под то, что осталось.

## 9. Алерты

- Направляй ops- и supply-chain-алерты в **канал, до которого агент не может дотянуться и который не может заглушить** (отдельный бот, отдельный чат или email). Скомпрометированный агент не должен иметь возможности выключить собственную тревогу.
- **Circuit breakers на фоновых циклах:** поднимай тревогу после N последовательных сбоев. Однажды publish loop молча лежал несколько часов.
- **Тестируй путь алерта end to end.** Алерт несколько дней падал с «chat not found».
- **Потерянный алерт — не зелёный статус.** Если отправка алерта не удалась, job завершается с ненулевым кодом.
- **Ignores истекают.** Ignore без срока — постоянная слепая зона.

## 10. Проектирование состояний сбоя

Для каждого самоуправляемого компонента (browser slots, фоновые циклы, sync jobs):

- Раздели сбои на **auto-recover** (инфраструктурный класс: потерянный supervisor, перезапуск, зависание — восстанавливаться после короткого grace-окна) и **needs-human** (auth, policy, конфликтующие правки).
- **Поднимай тревогу по всему, что застряло дольше ~30 минут**, независимо от класса.
- **Сохраняй историю сбоев** вне контейнера. Логи умирают при пересоздании; следующему расследованию нужны timestamps.
- Текст ошибки — это UX для агента: 403 с пометкой «permission-blocked» заставил агента часами повторять попытки. Говори, что делать дальше и когда остановиться.

Правила для cron и циклов (расписание, toolsets, approvals) — в [runtime-automation-governance](../skills/runtime-automation-governance/SKILL.md).

## 11. Цикл обучения

Закрывай каждое окно обслуживания, обновление или инцидент одними и теми же четырьмя шагами:

1. **Сначала закодируй исправления** в скрипты, строки sweep, тесты или guards для config. Фраза «не забыть…» — последнее средство.
2. **Обнови канонический документ**: у каждого факта один дом. Не пиши живое состояние в прозу: pins, digests, id jobs или «до <date>» устаревают за день; указывай на файл или команду, которые их доказывают.
3. **Напиши датированную неизменяемую ретроспективу** — это входные данные, а не канон — и в том же изменении перенеси её долговечные пункты в их дома.
4. **Найди устаревшие документы**, которые противоречат только что выученному.

Недельная версия этого цикла по реальным сессиям — [извлечение уроков за неделю](weekly-learning-extraction.ru.md). Если развёртывание за тебя обслуживает coding agent, его правила — в [руководстве оператора для coding agent](coding-agent-operator.ru.md).
