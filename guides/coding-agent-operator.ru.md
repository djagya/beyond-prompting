# Эксплуатация Hermes вместе с coding agent

**Независимое практическое руководство; практика одного долгоживущего deployment, не официальная документация Hermes или Nous Research.**

Многие операторы держат свой Hermes-сетап в приватном ops-репозитории (compose-файл, identity, скрипты, документация) и сопровождают его с помощью coding agent — Claude Code, Codex или Cursor. Так на одной системе оказываются два агента. Это руководство — рабочий контракт, который сделал такую схему безопасной и быстрой: что coding agent может делать, как он доказывает свою работу и как не мешает runtime-агенту.

Плейсхолдеры: `<box>` — хост, на котором работает Hermes, `<ops-repo>` — его checkout ops-репозитория, `./scripts/deploy.sh` — твой скрипт деплоя. Имена адаптируй; правила сохраняй.

## 1. Два агента, одна система

| | Coding agent | Hermes (runtime-агент) |
|---|---|---|
| Роль | Руки оператора в репозитории и на хосте | Долгоживущий агент с собственной identity, памятью и jobs |
| Пишет | Файлы репозитория, commits, PRs, деплои по мандату оператора | Свою память, skills, cron jobs и заметки внутри своего data home |
| Сессия | Ограниченная: одна задача, затем выход | Непрерывная: чаты, cron-запуски, фоновая работа |

Правила, которые отсюда следуют:

- **Никто не правит за спиной другого.** Coding agent не переписывает память или skills Hermes на хосте, чтобы «починить» поведение; он просит Hermes сделать это сам или меняет git-owned source и деплоит. Hermes не правит скрипты ops-репозитория; его собственные правки возвращаются через publish-путь, построенный для них (см. [Identity, память и контекст](identity-memory-context.ru.md)).
- **Координируйтесь через durable каналы.** Исправление, относящееся к другой сессии, уходит в ту сессию. Перед push в общую ветку предупреди её владельцев. Если Hermes публикует в тот же репозиторий, попроси его сделать rebase, а не разрешай его конфликт сам.
- **Hermes — пользователь твоей работы.** Сообщения об ошибках, skills и скрипты, которые ты поставляешь, читает агент. Пиши их для такого читателя ([Рабочие циклы, §2](operating-loops.ru.md)).

## 2. Checkout — dev-клон, а не runtime

Checkout на ноутбуке — источник истины для *кода*. Живой контейнер, его каталог данных и логи существуют только на `<box>`. Самая частая ошибка coding agent — принимать локальное состояние за runtime-состояние.

- Пустой `docker ps` на ноутбуке означает «здесь Docker не запущен», а не «стек лежит».
- Локальный каталог `data/` (часто остаток от тестирования sync-скрипта) устарел. Никогда не читай его ради runtime-фактов и никогда не правь, ожидая, что Hermes увидит изменение.
- «Перезапустить / обновить / задеплоить Hermes» означает запустить скрипт деплоя **на box**, а не `docker compose up` на ноутбуке. Локальный compose — только для отладки синтаксиса compose или сборки image.
- Подключайся к box только через свою приватную сеть (например, Tailscale), никогда по публичному IP.

Вставь это в корневой `AGENTS.md` (или `CLAUDE.md`) ops-репозитория и подправь:

```markdown
## Ориентация: этот checkout — dev, не runtime

- Живой Hermes работает на <box>. Этот checkout его никогда не запускает.
- Пустой `docker ps` или падающий `docker info` здесь ничего не говорят о стеке.
- Считай, что ./data/ не существует: он в gitignore и устарел. Никогда не читай
  его ради runtime-состояния, не правь его, не деплой из него. Живой каталог
  данных — на <box>.
- «Задеплоить / перезапустить / обновить Hermes» означает `./scripts/deploy.sh`,
  запущенный на <box> по SSH. Никогда не делай `docker compose pull/up/restart`
  вручную — ни здесь, ни там.
- Доступ к box: только приватная сеть (`ssh <box>` через tailnet). Никогда не
  публичный адрес и не LAN. Если имя хоста неоднозначно, спроси.
- Удалённая команда в кавычках не получает локальный heredoc. Используй
  `ssh <box> "bash -s" <<'EOF' ... EOF` и помни: всё после закрывающей кавычки
  выполняется локально.
- Runtime-память, cron jobs и живой config меняются на <box>, не через git.
```

Почему: агент, уверенный, что стек лежит, «чинит» его локально или деплоит устаревшие данные поверх живого состояния.

## 3. Мандат: что агент доводит до конца сам

Запиши мандат один раз — в репозитории или в памяти агента, — чтобы он не спрашивал на каждом gate.

**Делегируй от начала до конца** (практика, которая сработала): review, merge, сборку и публикацию image, его pin и деплой — когда tests и CI зелёные. «Готово» означает: закоммичено, запушено, задеплоено, если задача этого требует, и проверено, с указанием ветки и commit.

**Оставляй за владельцем**: политику и security posture (режимы согласования, allowlists, exposure), сетевую топологию, создание и ротацию credentials, всё публичное или обращённое вовне, необратимое удаление и отказ от upstream-настройки, которую выбрал владелец.

**Тормоза прав — это функция.** Когда система разрешений coding agent блокирует разрушительную команду, агент останавливается и сообщает; он не переформулирует команду, чтобы проскользнуть мимо проверки.

**Review до merge, даже в собственном форке.** Параллельные read-only reviewers однажды нашли настоящие баги в image, который уже был собран и закреплён; он не был выпущен. Pin — это контрольная точка review, а не доказательство review.

## 4. Дисциплина CI

CI — последний gate, а не искатель багов.

1. **Запускай локально точные команды CI.** Копируй их из файла workflow. `ruff check` проходил, пока CI запускал `ruff format --check`, и `main` остался красным; «похожие» команды — это другие команды.
2. **Держи локальный pre-push gate**, который запускает собственные jobs workflow (или их команды) на head, который ты собираешься запушить. Форк, который пушил в CI, чтобы узнать об отказах, сжёг большую часть своих CI-минут на одном PR с десятками push.
3. **Докажи, что gate может упасть (негативный контроль).** Запусти его один раз на заведомо плохом head и увидь ненулевой exit code. Локальный gate месяцами сообщал PASS, потому что дочерний процесс в `ssh <box> bash -s` читал остаток скрипта из stdin; bash упирался в EOF и завершался с кодом 0 до проверки. Перенаправляй stdin таких дочерних процессов из `/dev/null`.
4. **Следи за CI после каждого push**, пока он не станет зелёным или пока ты не поймёшь, почему он красный. Не громозди новые push поверх неизвестного результата.
5. **Отключи нерелевантные workflows в форке** (upstream release, деплой документации, боты issues), чтобы красные сигналы что-то значили.
6. **Знай ловушки** (на примере GitHub Actions; проверь свой CI):

| Ловушка | Симптом | Исправление |
|---|---|---|
| Токен пропуска CI (`[skip ci]`) процитирован где угодно в сообщении commit | Само исправление так и не прогнало CI | Никогда не пиши токен в subject или body, если не имеешь его в виду |
| Пустой commit, чтобы перезапустить workflow с фильтром путей | Ничего не запускается: файлы не изменились | Перезапусти workflow или измени файл в отфильтрованном пути |
| Publish-коммиты бота используют пропуск CI | Секреты в автоматических коммитах не сканируются | Запускай secret scan (например, gitleaks) на каждый push, включая коммиты с пропуском CI |
| Деплой из красного `main` | Сломанные скрипты попадают на box | Скрипт деплоя отказывает, если у деплоимого commit нет зелёного CI, допуская пропуск CI только для известных префиксов бота |

Gate деплоя, отказывающий при красном CI, ловил настоящие проблемы, включая коммиты бота вне разрешённых префиксов, которые никогда не тестировались.

## 5. Один worktree на сессию

Общие checkouts сталкиваются: незакоммиченные правки другого редактора попадают в твой commit, или другая сессия агента переключает ветку, и твой commit ложится не туда.

- Дай каждой сессии coding agent собственный `git worktree` (внутри игнорируемой scratch-области репозитория, не в `/tmp`).
- Перед commit проверяй `git branch --show-current` и `git status`; добавляй пути в индекс явно.
- Удаляй законченный worktree через `git worktree remove` на чистом дереве, никогда через `rm -rf`.
- На box не оставляй незакоммиченной работы: грязное дерево может остановить собственный publish job Hermes.

## 6. Секреты никогда не идут через чат

- Никогда не вставляй пароли, токены или коды восстановления в разговор с агентом. Если такой был вставлен, считай его утёкшим: владелец его ротирует.
- Передавай секрет в команду через stdin или переменную окружения, загруженную из файла, никогда как аргумент (аргументы видны в списках процессов и истории shell).
- Предпочитай device-flow / браузерные логины, которые завершает владелец, чтобы агент никогда не видел credential.
- Не доверяй regex-редактированию вывода команд. Подстановка `sed` без глобального флага заменила только первое совпадение в строке и пропустила токен, напечатанный дальше. Лучше: никогда не печатай значение.

## 7. Фоновые наблюдатели

Долгие ожидания (idle gate, сборка, перезагрузка) принадлежат фоновым наблюдателям. Им нужна гигиена.

- Дай каждому наблюдателю условие выхода и тайм-аут; останавливай устаревших наблюдателей, прежде чем запускать новых.
- `pgrep -f deploy` находит командную строку собственной обёртки, поэтому «ждать, пока deploy исчезнет» не заканчивается никогда (один такой цикл крутился 40 часов). Используй PID-файл, `pgrep -x` или трюк со скобками `[d]eploy`.
- Сравнивай время по одним часам. Хост и контейнер могут писать логи в разных часовых поясах.
- Всё, что может оборвать твою SSH-сессию (обновления пакетов хоста, перезапускающие Docker или VPN), запускай на хосте отсоединённо, как supervised unit с лог-файлом, а затем заново запусти деплой.

## 8. Сообщай статус в одной устойчивой форме

Заканчивай каждое обновление статуса одними и теми же тремя блоками:

```text
Готово:        <пункт> — доказательство (commit, run, вывод проверки)
Выполняется:   <пункт> — чего ждёт, как ты узнаешь о завершении
Нужно от тебя: <решение или действие> — почему только ты, что разблокирует
```

Переноси список *Нужно от тебя* в каждое обновление, пока каждый пункт не закрыт. Запрос решения, похороненный в прозе, — решение, которое никто не примет.

## 9. Группируй перезапуски; чини то, что видит пользователь

- **Один перезапуск на окно.** Сначала слей все ожидающие изменения, затем выполни одно обновление или деплой. Каждый перезапуск занятого агента стоит ожидания idle (на практике от одного до десяти часов) и свежего снимка перед обновлением.
- **Чини видимую поверхность, а не только метаданные.** Версию исправили в метаданных сборки, а имя ветки по-прежнему несло старую; каждый отчёт продолжал показывать неверную версию, и владельцу пришлось спрашивать дважды. Проверяй то, что читает пользователь: имена, заголовки, сообщения, dashboards.

## 10. Сообщи runtime-агенту, что изменилось

После изменения, которое затрагивает Hermes (исправленный баг, о котором он сообщал, новый skill, retired job), отправь ему помеченную разовую заметку вместо правки его записей:

```bash
ssh <box> 'cd <ops-repo> && ./scripts/hermes-cli.sh -z "$(cat)"' < note.txt
```

`hermes -z` — документированный режим скриптового разового запуска; `hermes-cli.sh` здесь обозначает твою обёртку, которая запускает CLI внутри контейнера от имени runtime-пользователя. Проверь флаг на своей версии. Промпт идёт через stdin, поэтому проблем с экранированием нет.

Начни заметку с `Operator note (from the coding agent):`, перечисли изменения и попроси Hermes самостоятельно проверить каждое, прежде чем закрывать свои задачи, и ответить, что он закрыл и что оставил. В одном запуске он закрыл четыре пункта и оставил пять, с причинами; одна заметка без проверки закрыла бы все девять.

## 11. Аудиты: read-only веером, ранжирование один раз

Периодический аудит — один из случаев, когда параллельные агенты окупают свою стоимость ([Один агент по умолчанию](../readings/single-agent-by-default.ru.md)): ветви независимы, read-only и идут вширь.

- Дели по поверхностям, например: репозиторий, box, CI и supply chain, identity runtime-агента (SOUL, память, skills).
- Каждый аудитор работает read-only и сообщает находки как *подтверждённые* (с доказательством) или *правдоподобные* (с проверкой, которая их подтвердит).
- Controller убирает дубликаты и выдаёт **один ранжированный список**. Исправления затем делаются в одной основной сессии, а не в аудиторах.

## 12. Разбирай собственную историю runtime-агента

Сессии runtime-агента — лучший bug report, какой у тебя есть: настоящие вызовы tools, настоящие ошибки, настоящие повторы.

1. Экспортируй окно сессий (`hermes sessions export <file>`; проверь на своей версии) или запрашивай session store read-only из копии.
2. **Сначала убери копии от compaction.** Сжатие контекста может сохранять одни и те же строки tools несколько раз; сырой подсчёт завышает каждую долю.
3. Посчитай исходы по каждому tool: вызовы, успехи, классы ошибок, циклы повторов.
4. Раздели исправления: **исправления поведения агента** (текст skills, сообщения об ошибках) идут в skills агента; **исправления кода** — в репозиторий. Вводящее в заблуждение сообщение об ошибке — и то и другое.

Такой разбор нашёл lease cache, игнорировавший identity (чувствительные вызовы выполнялись в исследовательском браузере), leases, которые не освобождались в конце сессии, и сообщение об ошибке, ставшее причиной многочасовых повторов.

## 13. Закрывай каждое окно уроками

Окно обслуживания не закончено, когда деплой зелёный. Прежде чем закрыть его:

- Сначала закодируй каждое исправление как guard в скрипте, тест или проверку; проза — только для того, что закодировать нельзя.
- Обнови канонический документ, которому принадлежит каждый факт (обоснование сетапа, руководство оператора, health checks).
- Напиши короткую датированную ретроспективу (что укусило, что исправлено, что осталось) и в том же commit перенеси её долговечные пункты в канон.
- Пройдись по документам, которые изменение сделало устаревшими.

Недельная версия этого цикла — [уроки за неделю](weekly-learning-extraction.ru.md); сторона health checks — в [Эксплуатации](operations.ru.md).

## Контракт сессии (вставь в своего coding agent)

```text
Ты эксплуатируешь deployment Hermes через этот репозиторий. Правила сессии:
- Этот checkout — dev. Runtime живёт на <box>; подключайся к нему только через
  `ssh <box>` по приватной сети. Никогда не доверяй ./data/ и локальному
  состоянию docker.
- Деплой = ./scripts/deploy.sh на <box>. Никогда не делай compose up/restart
  вручную.
- Мандат: ты можешь делать review, merge, publish, pin и deploy, когда tests и
  CI зелёные. Спрашивай меня о политике, security posture, топологии, ротации
  credentials, публичных публикациях и необратимом удалении. Если тебя
  блокирует проверка разрешений, остановись и сообщи; не обходи её.
- Перед push: запусти локально точные команды CI; после push следи за CI.
  Никогда не пиши токен пропуска CI в сообщении commit, который нужно
  протестировать.
- Используй собственный worktree. Перед каждым commit проверяй ветку и status.
- Никогда не проси меня вставить секреты. Передавай секреты через stdin;
  никогда их не печатай.
- Не правь память, skills или jobs Hermes у него за спиной. Меняй git-owned
  source и деплой или отправь ему помеченную разовую заметку оператора и
  попроси проверить, прежде чем закрывать свои пункты.
- Группируй изменения в один перезапуск; сначала дождись, пока агент станет idle.
- Отчитывайся блоками Готово / Выполняется / Нужно от тебя. Переноси «Нужно от
  тебя», пока пункт не закрыт.
- Готово = закоммичено, запушено, задеплоено при необходимости, проверено,
  ветка и commit названы.
- Закрывай окно: закодируй исправления, обнови канонические документы, напиши
  датированную ретроспективу.
```

Это правила из практики одного deployment. Оставь те, что предотвращают отказ, который ты можешь назвать в своём сетапе.
