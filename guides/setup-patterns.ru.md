# Приёмы сетапа, которые стоит перенять

**Практические заметки из кастомизированного Hermes-сетапа Данила; не обязательный шаблон развёртывания.**

Это карта переносимых решений, а не копия приватной конфигурации. Контроли нужно адаптировать к своим аккаунтам, инструментам и рискам.

Начни с [агентского входа](agent-start.ru.md): карта возможностей и запасные маршруты. Достаточно одного controller; приватные профили, workers, memory services и deployment paths не являются предпосылками. Конкретные контракты исполнения — в [рабочих циклах](operating-loops.ru.md). Конкретный deployment — в [эталонном сетапе](setup-reference.ru.md), [эксплуатации](operations.ru.md), [идентичности, памяти и контексте](identity-memory-context.ru.md) и [Hermes и coding agent](coding-agent-operator.ru.md).

## 1. Изучать опыт, затем механизм

Используй [извлечение уроков за неделю](weekly-learning-extraction.ru.md): сначала ревью, затем проверка текущих владельцев, внедрение — после ограниченного мандата. Неудачный результат может означать конфликт инструкций или отсутствие нужной возможности, а не недостающее правило.

## 2. Один владелец конечного результата

Controller сохраняет интеграцию, внешние полномочия и итоговую проверку. Workers получают ограниченные задания по своим реальным возможностям. [Один агент по умолчанию](../readings/single-agent-by-default.ru.md) помогает решить, окупается ли делегирование. Уведомление или handoff ещё не является доставкой результата.

## 3. Разделять текущее состояние, процедуры и историю

Действующее решение имеет одного подходящего владельца. Процедуры живут в reusable skills; состояние проекта — в проектных артефактах; приватные свидетельства остаются приватными. Исторический пересказ не должен конкурировать с последующей пользовательской коррекцией. Source и deployed state проверяются отдельно.

## 4. Проверять заказанную работу

Докажи полезный исход, а не только успешный вызов инструмента: документ должен читаться, визуальная карта — оставаться визуальной, доступ — подтверждаться безопасным запросом, temporal-ответ — датированным свидетельством. Непройденные проверки называй явно.

## 5. Явные внешние границы

Возможность не равна полномочию. Неавторизованный браузер не доказывает отсутствие API-маршрута; настроенный credential — работающий доступ. Сохраняй origin binding, native secret transport, подтверждения и безопасное поведение при неоднозначном результате. См. [hardening guide](hermes-hardening.md).

## 6. Использовать существующего lifecycle owner

Сначала штатные jobs, supervision и recovery, затем — дополнительный watcher, если его необходимость доказана. Controller должен иметь ясное условие остановки: результат получен, настоящий блокер, ожидаемая внешняя работа или исчерпан ограниченный бюджет. Не превращай ожидание workers и CI в busy polling.

## Форк Hermes

[Форк Данила](https://github.com/djagya/hermes-agent) — это upstream Hermes плюс эксплуатационные исправления для одного долгоживущего Docker-развёртывания: постоянно работающий messaging gateway, несколько profiles, много cron jobs, secret manager и агент, который сам правит свои skills. Release-ветки отрезаются от upstream release tags и называются по версии upstream, которую они поставляют; каждый релиз публикуется как container image, закреплённый по digest. [Upstream Hermes](https://github.com/NousResearch/hermes-agent) остаётся исходным проектом.

Состав веток и включение изменений в upstream меняются. Заметка не утверждает, что каждое изменение форка отсутствует upstream, требуется для этих методов или подходит чужому развёртыванию. Перед использованием проверь выбранную ветку, diff с актуальным upstream, tests и release notes; выбери известную ревизию. Default branch форка не обязательно совпадает со сборкой, которую сейчас использует владелец.

### Что меняет форк

Таблица сравнивает release-ветку форка с upstream `main` по областям. CI-обвязка, которая не меняет того, что получает пользователь, опущена. «Только в форке» значит, что в upstream `main` на момент написания не было эквивалентного кода. Перепроверь, прежде чем полагаться на любую строку.

Запуски по расписанию тоже их видят. См. [Identity, память и контекст](identity-memory-context.ru.md). | Только в форке. |

Некоторые прежние изменения форка **больше не являются отличиями**, потому что upstream исправил ту же проблему: разбор литералов списков и mapping в `hermes config set` (upstream «fix(config): parse list/mapping literals in hermes config set» и «config set refuses a wrong-shaped value for a list/mapping key»), исправление RCE GitSpawn через config репозитория, которое форк нёс до того, как оно попало в его базовый релиз, утечка маркеров делегирования через snapshot терминала и явный admin для `/goal gate add`. Более старые изменения форка в цепочках fallback для делегирования, лимитах хранилища checkpoints, lineage терминала и границах записи Home Assistant тоже больше не отличаются от upstream в дереве форка. Перед выводом в любую сторону проверь актуальный upstream.

### Компромиссы при использовании форка

- **Один мейнтейнер, одно развёртывание.** Изменения выбирает, проверяет и выпускает один человек для одного профиля развёртывания. Некоторые из них специфичны для него: image требует имя агента владельца как автора локально созданных skills, вшивает MCP-серверы для сервисов владельца и несёт клиент управления браузером.
- **Между релизами форк отстаёт от upstream.** Релиз следует за upstream tag, полным прогоном тестов и локальным CI gate. Upstream `main` движется быстро, поэтому исправления, попавшие в upstream после релиза форка, в том числе исправления безопасности, приходят в форк только со следующим релизом или перенесённым патчем.
- **Ты доверяешь второму издателю.** Image собирают workflows владельца форка и публикуют из его registry-аккаунта, в дополнение к исходникам Nous Research. Закрепляй по digest и проверяй attestation; image только для amd64.
- **Документация и данные расходятся.** Официальная документация неверна для поведения, которое есть только в форке (managed scope описан как замок; слот `ARCHITECTURE.md` не документирован). Форк добавляет колонку в базу сессий и придерживает одну upstream-миграцию индекса, поэтому возврат на upstream может при первом открытии запустить эту миграцию и живую перестройку индекса. Проверяй переход на копии.
- **Contribution PRs уходят в upstream, поэтому разница должна сокращаться, но только когда upstream принимает или заменяет изменение.** Исправления предлагаются отдельными PR, перенесёнными на актуальный upstream `main`; несколько из них открыты, и на момент написания ни один не был влит. Совпадения пока возникали, когда upstream сам исправлял ту же проблему. Каждый релиз выбрасывает carryovers, которые уже попали в upstream.

### Выбор между форком и upstream

Стокового upstream достаточно для установки на ноутбук или desktop, недолгоживущего gateway или gateway с одним profile, лёгкого использования cron, работы без secret manager и любой машины не на amd64. Он также первым получает исправления и совпадает с официальной документацией. Изменения форка важны для профиля, под который он сделан: постоянно работающий Docker gateway с несколькими profiles и множеством cron jobs, хранилище сессий в несколько GB, secret manager с rate limit, агент, который правит свои skills под write approval, и оператор, которому нужны закрепление по digest, SBOM и provenance. Поэтому форк лучше для этого профиля развёртывания, а не лучше вообще. Ради одного исправления перенести этот патч на upstream может обойтись дешевле, чем принять весь форк.

Read-only запрос на адаптацию для агента:

```text
Проведи инвентаризацию моей установки Hermes, ничего не меняя: кто владеет
кодом (Git checkout, container image, другая упаковка), terminal и browser
backends, работающая версия и её source revision или image digest.
Для каждого значимого инструмента сопоставь способность -> полномочие ->
проверенный доступ. Сравни названную мной ревизию форка с моей upstream
базой. Предложи инкрементальный набор изменений с проверками приёмки и
откатом (предыдущий digest или revision). Ничего не устанавливай, не
обновляй, не перезапускай и не переключай сборку.
```
